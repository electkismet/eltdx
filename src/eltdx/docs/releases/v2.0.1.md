# v2.0.1

`v2.0.1` 是相对 `v2.0.0` 的兼容修复版本。现有模块化 API 名称没有变化，从 `v2.0.0` 升级时不需要迁移调用方式。

本次主要修复三件事：成交明细能正确区分集合竞价过程和实际成交、09:25 正式撮合会选择正确的数据源、自动分页不会因为主站返回条数变化而漏数据。

## 更新说明

### 1. 成交明细不再混淆竞价过程和实际成交

当日成交明细 `0x0fc5` 和历史成交明细 `0x0fc6` 的原始返回中，普通成交、集合竞价过程快照和 09:25 正式撮合混在一起。`v2.0.1` 会明确标记每条记录：

| `event_kind` | 说明 |
| --- | --- |
| `trade` | 盘中的实际成交 |
| `auction_snapshot` | 集合竞价过程中的虚拟撮合快照，不是实际成交 |
| `opening_match` | 09:25 产生的正式开盘撮合 |

原始记录仍完整保留。需要直接筛选时可使用：

```python
page = client.trades.all_today("sz000001")

snapshots = page.auction_snapshots  # 集合竞价过程快照
opening = page.opening_matches      # 09:25 正式撮合
```

### 2. 09:25 查询会自动选对当日或历史接口

```python
result = client.trades.opening_match_history("sz000001", "2026-08-13")
```

SDK 先读取主站当前保存的交易日，再决定数据来源：

- 查询主站当前交易日：使用当日成交明细 `0x0fc5`。
- 查询其他交易日：使用历史成交明细 `0x0fc6`。
- 只返回 `opening_match`，不会把竞价过程快照误当成 09:25 正式成交。

因此在凌晨、周末或节假日查询时，不会再因为电脑日期与主站交易日不同而选错接口。

### 3. 自动分页不会因为“短页”提前停止

主站实际单页上限分别是代码表 1600 条、K 线 800 条、成交明细 1800 条。`v2.0.0` 的部分分页逻辑看到返回条数少于请求条数就认为已经结束，主站临时少返回时可能漏掉后续数据。

`v2.0.1` 改为按本页实际返回条数继续向后查询，直到主站返回空页才结束，并按真实单页上限校验参数。

## 竞价相关接口怎么选

| 你要的数据 | 使用接口 | 返回内容 |
| --- | --- | --- |
| 主站当前交易日的集合竞价过程 | `client.auctions.series()` | 集合竞价过程明细，不依赖它提供 09:25 正式撮合 |
| 主站当前交易日的完整成交明细 | `client.trades.all_today()` | 普通成交、竞价过程快照、09:25 正式撮合 |
| 指定历史交易日的完整成交明细 | `client.trades.all_history()` | 普通成交、竞价过程快照、09:25 正式撮合 |
| 只取当日 / 历史 09:25 正式撮合 | `client.trades.opening_match_today()` / `opening_match_history()` | 固定从对应成交明细中返回正式撮合 |

`client.trades.today()` 和 `client.trades.history()` 每次只返回一页，主要用于手动分页、抽样查询或控制单次请求量。需要完整成交明细时，应使用自动翻页并合并结果的 `all_today()` 或 `all_history()`。

这里的“当日”是主站当前保存的交易日，不一定等于电脑当前的自然日。例如周五收盘后的周六凌晨，主站的“当日”通常仍是周五。
