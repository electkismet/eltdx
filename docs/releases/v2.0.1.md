# v2.0.1

`v2.0.1` 补全成交明细里的集合竞价记录解析，修正 09:25 正式撮合的数据源选择，并增强分页可靠性。

## 成交明细里的竞价记录

当日 `0x0fc5` 和历史 `0x0fc6` 共用一套混合记录格式。解析器现在明确区分：

- `trade`：普通成交。
- `auction_snapshot`：`status=8` 的集合竞价过程快照，不是实际成交。
- `opening_match`：09:25 正式开盘撮合。

`TradePage.auction_snapshots` 和 `TradePage.opening_matches` 可以直接筛选对应记录；原始协议字段仍完整保留。

## 09:25 当日与历史选源

```python
result = client.helpers.auction_0925("sz000001", "2026-08-13")
```

SDK 会先读取握手中的主站交易日：

- 目标日期等于主站交易日时使用当日成交明细 `0x0fc5`。
- 其他日期使用历史成交明细 `0x0fc6`。
- 只返回 `opening_match`，不会把 `status=8` 竞价快照当作正式成交。

这里不使用本机自然日猜测，因此凌晨、周末和节假日也不会误选数据源。握手无法提供主站日期时会明确报错。

## 当日接口名称

公开入口继续使用“当日”名称：

```python
client.minutes.today("sz000001")
client.trades.today("sz000001")
client.trades.all_today("sz000001")
client.auctions.series("sz000001")
```

“当日”指主站当前保存的交易日数据，不保证等于电脑自然日。`current()` 和 `all_current()` 不是公开兼容入口。

## 分页修复

- 代码表单页上限为 1600。
- K 线单页上限为 800。
- 成交明细单页上限为 1800。
- 自动分页按服务端实际返回条数推进，并在收到空页时结束，避免服务端调整单页返回数量后静默漏数。
